# WDT再起動ループ：第三者レビュー用・事象整理書（2026-09-15）

Raspberry Pi Pico 2 Wファーム（BTstack Classic + Switch Pro Controllerエミュレーション）で発生中のWDT再起動について、
別AIの意見を求めるための事実整理。推測と確定を分離して記載する。

## 1. 環境・前提

- 機器: Raspberry Pi Pico 2 W（RP2350）、Pico SDK 2.3.0、BTstack同梱版
- 相手: Nintendo Switch 2（peer `3C:A9:AB:37:CF:D3`、終始同一）
- 自MAC: `7C:BB:8A:D3:FD:CA`（OUI固定＋基板ID由来、下3B固定）
- WDT: `watchdog_enable(2000, 1)`、給餌は1ms周期BTstackタイマ駆動の`poll_tick()`末尾（`watchdog_update()`）
- 給餌停止→約2.0秒後にWDT再起動（`wdt=1`で識別可能）
- Core1: 製品側はprintfなし・BT/CYW43/Flash不使用・ポーリング＋短mutexのみ（関与の形跡なし）
- 比較対象（正常系の証人）: 同一Switchでwakecon実装はSUB完走・長時間維持（A1 00空レポート方式でも動作する事実あり）

## 2. 確定している時系列事実（ログ証拠付き）

### 2.1 初期発見：open時TLV書込とWDT死の相関
- HID openコールバック内でhost住所録（6B、`BCHO`タグ）をTLVへ保存していた版は、open後に沈黙→WDT再起動を反復
- 保存を停止した版（4:24）では死亡停止、60秒以上生存、BCON（1秒生存表示）継続
- この時点の暫定結論は「保存処理がタイマ系を破壊」だった

### 2.2 再発（Phase-3テストログ `log/COM3_2026_09_14.23.51.02.287.txt`）
3セッション：
- S1: conn→暗号化→**約2.0秒の完全沈黙**→WDT（HID openなし、**Flash書込ゼロ**）
- S2: open＋初回host保存（`host saved (n=1)`）→**約2.0秒後にWDT**（保存はFlashに到達したことが次起動の`host=1`で証明済み）
- S3: 保存スキップ（dedupe一致）→ SUBフル完走、生存
- 教訓1：書込なし死が存在する（＝書込単独犯説は不十分）。教訓2：初回書込→死は再現する

### 2.3 定量A/B（各UF2は単一変数、ビルド＋復元証明済み）
- W0（統制・現行treeそのまま）`log/switch-bcon-w0-control.uf2`：安定、WDTなし
- W1（host書込をopen→3秒後タイマへ遅延）`log/switch-bcon-w1-defer.uf2` → 実機ログ `log/COM3_2026_09_15.00.45.36.087.txt`：
  保存→約2.0秒後WDT死を **3/3再現**（51.2→53.2、58.5→60.5、12.2→14.2）。
  結論：BTstackイベントコールバック内かタイマ内かは無関係。BT動作中のFlash書込自体が殺す
- W3（IRQ駆動breadcrumb計装のみ）→ 実機で安定動作（WDTなし、正常切断のみ）
- W4（遅延＋breadcrumb複合）→ post-mortem 4/4完全一致：`stage=2`（`poll_tick`は給餌直前まで完走）、
  `poll`停止＋IRQ進行、`ev`は計装caveatで参考値。結論：死に場所は`poll_tick`本体外
  （inbox-drain無限ループ・exec/flush・USB・link wedged説は棄却）
- W5（遅延＋書込時間計測）→ 実機ログ `log/COM3_2026_09_15.01.44.40.359.txt`：
  `store begin` → **`store dt_us≈2070 rc=0`** → `host saved` → 約2.0秒後WDT死、**5/5同一**
- 通算：**書込→死 9/9**（Phase-3 S2＋W1×3＋W5×5）、**無書込→生存 約12セッション**

## 3. 死亡シグネチャ（全例共通）

1. 最終マイルストーン（暗号化完了 or Flash保存完了）から**約2.0秒後**に再起動（＝WDTタイムアウトきっかり）
2. BCON（1秒タイマ）を含むタイマ系がマイルストーン時点で停止。以後のアプリログ出力なし
3. Fault reporter沈黙（非Fault停止として確定済み）
4. 書込自体は約2msで`rc=0`正常完了し、後続ログも出力される（＝書込中のストール死ではない）
5. WDT死であること（`wdt=1`）以外、事後情報なし

## 5. 筆者の現時点の考察（未確定・意見を求めたい部分）

### 第一候補：Flash書込時の割り込みブラックアウト＋CYW43ドライバの状態機械破損
`flash_safe_execute`は全割り込み禁止＋Core1ロックアウトで約2ms実行する。
暗号化直後・L2CAP確立前後のシグナリングバースト中に2msブラックアウトすると、
CYW43連携の送受信状態機械（再送タイマ・パケットプール）が応答待ちのまま固まり、
以後run loopが進まなくなる、という筋書き。BCON停止・ログ沈黙・2秒後WDTと整合する。
弱点：Session-1型（書込なし死）の説明にはBTstack内部ログ（T4で削除済み）が不可欠で、
現手持ち証拠ではL2CAP側の進行状況が不可視。W6取得で確定化したい。

### 第二候補：TLV bank層の遅延作用
`store`直後はrc=0でも、bank整理（erase/compaction）が遅延実行され、その際の
長時間割り込み停止が止めを刺す。弱点：9回すべて約2.0秒という正確さが、
erase時間のバラつきと合いにくい。

### 未解決の謎（特に意見がほしい）
1. Session-1型の死（書込ゼロ・暗号化→約2秒沈黙→WDT）にFlashは無関係に見える。
   同一機序か、別機序か。W6のバイト比較が鍵になると考えているが、他に見るべき点はあるか
2. T3の鍵削除（Flash消去系）が2回発火しても死ななかったのはなぜか。
   現説明：非bondingで鍵が残留しないため実質no-op。妥当か
3. 起動直後のwipe削除（Flash消去）は生存するのに、BT動作中のprogramが致命的なのはなぜか。
   「コネクション有効時の書込がダメ」という整理で十分か、それとも割り込み禁止時間の問題か
4. 恒久修正として「BT動作中のFlash変更を全面禁止し、dirty-flag＋無線停止中の単一workerへ集約」
   を考えている。妥当か、見落としている安全な書込窓はあるか
